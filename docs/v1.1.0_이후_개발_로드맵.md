작성일: 2026-07-28

릴리즈 커밋: `151cb3f8a38912463538fed04cc2135eb48977d0`

## 1. 문서 목적

이 문서는 v1.1.0 Full Futures 릴리즈 이후의 개발 순서와 완료 조건을 정의한다.

이전 문서인 `최종 릴리즈 후 해야할 작업. 0727.md`는 v1.0.0 Spot 릴리즈 직후의
판단과 아이디어를 보존하는 원본이다. 이전 문서는 삭제하거나 덮어쓰지 않는다.
실제 작업은 이 문서를 기준으로 진행한다.

이번 로드맵의 핵심 목표는 다음과 같다.

1. v1.1.0에서 증명한 exact parity 계약을 리팩터링 회귀 기준으로 동결한다.
2. 검증 상태, 인증 fingerprint, evidence 수명주기를 하나의 일관된 모델로 만든다.
3. 대형 Python 및 Rust 모듈을 동작 변경 없이 단계적으로 분리한다.
4. 새 구조에서 병목을 다시 측정하고 증명된 최적화만 적용한다.
5. 디스크 정리, 결과 artifact, CI 및 장시간 인증을 제품 기능으로 완성한다.
6. 최종 wheel이 확정된 뒤 최신 Spot과 Futures를 같은 candidate로 인증한다.
7. 같은 전략과 binary로 봉인된 Spot+Futures 통합 Full X7 릴리즈를 만든다.
8. 이후 NFI 변경은 공식 fallback과 범용 state-machine IR로 지속 대응한다.

## 자동 실행 제어

이 문서는 방향과 완료 정의를 제공한다. 실제 진행 상태와 검증 명령은 다음 두
machine-readable 파일을 사용한다.

- `planning/roadmap-state.json`
  - 작업 순서, 의존성, 상태, manual gate, 결과 evidence
- `planning/acceptance-commands.json`
  - 작업 종류별 필수 검증 명령, 실행 위치, timeout, 결과 artifact

새 세션이나 resume은 반드시 다음 순서로 시작한다.

1. 이 문서를 처음부터 끝까지 읽는다.
2. `planning/roadmap-state.json`을 읽고 JSON 유효성을 확인한다.
3. `planning/acceptance-commands.json`을 읽고 JSON 유효성을 확인한다.
4. Git worktree, 활성 프로세스, 사용자 소유 untracked 파일을 확인한다.
5. `active_task_id`가 있으면 새 작업을 선택하지 않고 해당 작업부터 복구한다.
6. 활성 작업이 없으면 dependency가 모두 완료된 첫 번째 `pending` 작업만 선택한다.
7. 한 번에 한 작업만 `in_progress`로 둘 수 있다.

명령 예시:

```bash
jq empty planning/roadmap-state.json
jq empty planning/acceptance-commands.json
jq -r '.active_task_id // "none"' planning/roadmap-state.json
jq -r '
  .tasks[]
  | select(.status == "pending")
  | [.order, .id, .title, (.depends_on | join(","))]
  | @tsv
' planning/roadmap-state.json
```

### 작업 선택 알고리즘

```text
사용자의 최신 지시 확인
→ active_task_id 확인
→ 활성 작업이 있으면 checkpoint와 worktree 검증 후 resume
→ 활성 작업이 없으면 order 순으로 pending 작업 탐색
→ depends_on이 전부 completed인지 확인
→ manual_gate면 실행하지 않고 승인 요청
→ 선택한 작업만 in_progress로 전환
→ preflight acceptance 실행
→ 구현
→ completion acceptance 실행
→ evidence 경로와 SHA 기록
→ commit SHA 기록
→ completed 전환
→ 다음 eligible task 계산
```

사용자의 직접 지시는 항상 이 로드맵보다 우선한다. 다만 사용자가 명시적으로
정확성 계약을 변경하지 않은 상태에서 exact parity, evidence 보호 또는 fail-closed
규칙을 완화해서는 안 된다.

### 상태 전이

허용 상태:

- `pending`
- `in_progress`
- `waiting_external`
- `waiting_approval`
- `completed`
- `blocked`
- `superseded`

정상 전이:

```text
pending → in_progress
in_progress → waiting_external → in_progress
in_progress → waiting_approval → in_progress
in_progress → completed
in_progress → blocked
pending → superseded
```

완료 조건을 통과하지 못한 작업을 `completed`로 바꾸지 않는다. 실패가 발생하면
기존 성공 evidence와 이전 task event를 덮어쓰지 않고 새 event를 추가한다.

### Manual gate

다음 작업은 자동으로 외부 상태를 변경하지 않는다.

- 공식 장기 Oracle 신규 실행
- GitHub RC 또는 stable 공개
- immutable evidence 삭제
- `.nfi clean` 실제 삭제
- branch protection 변경
- PyPI 또는 다른 registry 게시
- 최신 Spot+Futures 통합 릴리즈

`manual_gate=true` 작업은 필요한 입력, 예상 시간, 변경 대상, rollback 가능 여부를
정리한 뒤 사용자 승인을 받아야 한다.

### Resume 규칙

1. 활성 PID, user service, Docker container를 먼저 확인한다.
2. 완료된 checkpoint의 identity와 SHA를 검증한다.
3. 완료된 stage는 다시 실행하지 않는다.
4. 파일이 변조됐거나 상태가 모순되면 덮어쓰지 않고 fail-closed한다.
5. 장시간 작업은 command identity, 시작 시각, output, log, PID 또는 service를
   state event에 기록한다.
6. 장시간 작업이 정상 실행 중이면 불필요한 반복 polling을 하지 않는다.
7. 작업 종료 후 exit code, result SHA, peak RSS, evidence 경로를 수집한다.

### Acceptance 규칙

- 각 task는 `acceptance_profile`을 가진다.
- profile에 연결된 모든 `required=true` 명령이 통과해야 한다.
- `availability=planned` 명령은 해당 task가 완료되기 전에 구현돼야 한다.
- OS 전용 명령은 해당 OS CI 결과 URL과 commit SHA를 evidence로 기록한다.
- 장기 성능 명령은 일반 개발 acceptance에 포함하지 않고 manual gate에서 실행한다.
- 결과 SHA가 바뀌면 성능 개선 여부와 무관하게 작업을 완료하지 않는다.

### 상태 파일 갱신 규칙

상태 변경 시 다음을 함께 갱신한다.

- 최상위 `revision`
- `updated_at`
- `active_task_id`
- task의 `status`
- `started_at` 또는 `completed_at`
- `commit_sha`
- `evidence`
- append-only `events`

State 파일에는 access token, API key, 개인 경로의 민감 정보, 거대한 로그 본문을
넣지 않는다. Evidence에는 경로, 크기, SHA, run URL 같은 참조만 기록한다.

## 2. 변경할 수 없는 개발 원칙

1. 공식 Freqtrade는 최종 정답지다.
2. exact parity가 없는 근사 지원은 추가하지 않는다.
3. 처음 보는 전략 의미론은 명확한 진단과 함께 `fail-closed`한다.
4. 페어, 날짜, 전략 SHA 또는 특정 결과를 런타임에 하드코딩하지 않는다.
5. Golden SHA는 회귀 검증용 증거이며 런타임 분기 조건으로 사용하지 않는다.
6. 리팩터링과 알고리즘 최적화를 같은 커밋에 섞지 않는다.
7. 한 커밋은 한 책임만 이동하거나 한 병목만 개선한다.
8. 글로벌 wallet, slot, order, protection, pair-lock의 시간순 처리를 보존한다.
9. equal-timestamp pair ordering을 임의로 병렬화하지 않는다.
10. 변경 전후 surface SHA와 필요한 full-state projection SHA가 같아야 한다.
11. 성능은 같은 input과 binary에서 3회 측정하고, 5% 이상 퍼지면 5회 측정한다.
12. 평균 대신 중앙값, 최대 process-tree RSS, swap, disk I/O를 기록한다.
13. Cold 성능을 숨기고 warm-cache 성능만 제시하지 않는다.
14. 공식 ZIP, 인증서, surface, trace 및 release evidence는 제자리에서 수정하지 않는다.
15. 정리 명령은 활성 실행과 인증 evidence를 기본적으로 삭제하지 않는다.
16. 브랜치와 커밋 이름에는 도구나 에이전트 이름을 넣지 않는다.

## 5. 전체 실행 전략

모든 작업을 하나의 거대한 목표로 묶지 않는다. 다음 여섯 마일스톤을 순서대로
완료한다.

```text
M1. v1.1 계약과 evidence lifecycle 동결
→ M2. Python 책임 분리
→ M3. Rust 책임 분리
→ M4. 재측정과 최적화
→ M5. 제품 UX와 운영 자동화
→ M6. 최신 Spot+Futures 통합 Full X7 인증
```

기존 Full Futures 공식 Oracle은 M1~M5 동안 다시 실행하지 않는다.

## 6. M1 — v1.1 계약과 evidence lifecycle 동결

### 6.1 Regression contract

하나의 versioned regression manifest에 다음을 묶는다.

- schema version과 대표 문서 SHA
- public CLI 명령과 exit code
- 안정적인 오류 code
- v1.0.0 Spot release certificate identity
- v1.1.0 Futures release certificate identity
- bounded Spot/Futures surface SHA
- 9개 Futures full-state fixture SHA
- resume 완료, 중단, 변조, checkpoint 재사용 시나리오
- unsupported semantics의 fail-closed 결과
- result artifact의 필수 파일과 schema
- release asset 이름, 크기, SHA

규칙:

- manifest는 원본 evidence를 참조하고 복제하지 않는다.
- 의도적인 계약 변경은 schema 또는 contract version을 올린다.
- golden hash는 테스트 검증값이며 런타임 거래 로직에서 읽지 않는다.

완료 조건:

- 단일 검증 명령으로 contract 전체를 검사할 수 있다.
- 리팩터링 전후 manifest 검증 결과가 동일하다.
- 변조된 evidence 하나를 즉시 거부하는 회귀 테스트가 있다.

### 6.2 검증 상태 ledger

이전 문서의 SHA 상태 모델과 검증 3단계 모델을 중복 구현하지 않고 하나로 합친다.

전략 revision 상태:

- `latest_checked`
- `quick_verified`
- `release_certified`

실행 상태:

- `prepared`
- `native_complete`
- `quick_verified`
- `release_certified`
- `blocked_unsupported_semantics`
- `failed`

각 레코드가 포함할 identity:

- upstream repository와 commit
- strategy source SHA
- canonical strategy IR와 hot callback IR SHA
- config와 ordered pairlist SHA
- data seal과 market snapshot SHA
- timerange와 mode contract
- Freqtrade image/index/platform digest
- package, wheel, native binary SHA
- 생성 시각과 evidence 경로

규칙:

- 새 fingerprint는 기존 레코드를 덮어쓰지 않는다.
- compatibility 실패가 마지막 성공 상태를 지우지 않는다.
- Full 인증 SHA와 최신 upstream SHA가 다른 것은 정상 상태다.
- HTML과 CLI는 “최신 확인”과 “Full 인증”을 같은 배지로 표시하지 않는다.

### 6.3 Evidence index와 안전한 clean dry-run

먼저 삭제 기능이 아니라 분류와 dry-run만 만든다.

분류:

- 활성 실행 및 checkpoint
- release certificate와 bundle
- 공식 Oracle과 Freqtrade ZIP
- 사용자가 보존한 run
- 재생성 가능한 vector/cache
- 중단 또는 실패 run
- 임시 Arrow/Docker spool
- 오래된 build와 calibration

`clean --dry-run` 필수 출력:

- 분류별 파일 수와 logical/allocated bytes
- 삭제 가능 여부와 보호 이유
- 예상 회수량
- 활성 PID, lock, service
- evidence identity
- audit JSON 경로

Fail-closed 조건:

- `.nfi` 소유 범위를 벗어난 경로
- symlink를 통한 외부 경로
- 활성 PID 또는 lock
- release evidence 또는 공식 ZIP
- identity가 불완전한 인증 디렉터리

실제 삭제는 dry-run 분류와 evidence 보호 테스트가 완료된 뒤 별도 커밋으로 추가한다.

### 6.4 Release workflow certificate gate

현재 build-once, byte-identical RC/stable 흐름은 유지한다.

장기 certificate를 GitHub artifact에만 의존하지 않는다. 장기 보존 원본은 immutable
evidence storage와 GitHub Release에 둔다.

### 8.2 M8-01 저장공간 수명주기와 실제 정리

개발·성능 측정·5년 인증 과정에서 재생성 가능한 벡터와 cache hard link가 여러
작업 디렉터리에 남아 실제 `.nfi` 사용량이 172 GiB까지 증가했다. 완료 후 중첩
`vectors`와 vector cache 363개를 제거해 14 GiB로 축소했으며, 인증서, 보고서,
공식 Oracle, 원본 캔들 데이터와 공용 cache는 보존했다.

일반 사용자에게 같은 문제가 누적되지 않도록 M1-03의 read-only audit 후속으로
다음 계약을 구현한다.

- logical pathname bytes와 hard-link 중복을 제거한 physical bytes를 함께 계산한다.
- 실제 회수량은 삭제 대상 밖의 hard link가 없는 inode만 포함한다.
- `clean --apply`는 직전에 새 audit를 만들고 fail-closed 상태에서는 실행하지 않는다.
- cache, 실패·중단 run, 임시 spool, build/calibration만 기본 삭제 대상으로 삼는다.
- 완료 run은 명시적 opt-in 없이는 삭제하지 않으며 preserve marker가 항상 우선한다.
- release certificate, bundle, 공식 Oracle과 Freqtrade ZIP은 opt-in으로도 삭제하지 않는다.
- 새 일반 사용자 run은 관리되는 `.nfi/runs` 아래에 두어 clean 정책 범위에 포함한다.
- cache 예산은 파일시스템 여유와 명시적 사용자 설정으로 결정하며 전략, 페어,
  기간 또는 예상 결과에 따른 분기를 두지 않는다.
- 모든 실제 삭제는 audit SHA와 삭제 항목을 포함한 receipt를 남긴다.

완료 조건은 hard-link 회계, 외부 link 비회수, dry-run 무변경, apply 삭제,
활성 실행 거부, evidence 보호, 완료 run opt-in, preserve override, cache budget
테스트와 전체 Python/static 검증 통과다.

2026-07-29 구현과 검증을 완료했다.

- 실제 개발 `.nfi`에서 새 audit가 cache, 실패 run, build/calibration 6개만
  선택했고 활성 PID, lock, 소유 service, managed container는 모두 0이었다.
- audit SHA를 고정한 apply receipt를 남기고 할당 기준 4,211,195,904 bytes를
  추가 회수해 14 GiB에서 9.3 GiB로 축소했다.
- apply 후 새 dry-run의 회수 가능 logical/allocated bytes는 모두 0이다.
- 부분 인증 identity issue가 있는 단위는 그대로 보호하되 무관한 cache 정리를
  전역 차단하지 않도록 단위별 fail-closed 경계를 적용했다.
- hard-link 내부 중복, 보호 run 공유 inode, `.nfi` 외부 link, 완료 run opt-in,
  preserve override, 모든 ZIP 보호, 활성 runtime 거부, cache budget을 테스트했다.
- 전체 Python 452개, 저장공간 20개, 사용자 흐름 42개 테스트와 Ruff,
  basedpyright를 통과했다. 시뮬레이션 동작이나 최적화 분기는 변경하지 않았다.

## 12. M9 — v1.2.0 제품 릴리즈

사용자는 2026-07-29에 post-v1.1 작업 전체를 `v1.2.0`으로 공개하도록 승인했다.
앞서 제외한 M6의 최신 동일-candidate 5년 Spot/Futures 재인증은 다시 포함하지 않는다.

따라서 v1.2.0은 다음 경계를 갖는 `product` 릴리즈다.

- 패키지와 CLI 버전은 `1.2.0`이다.
- v1.0.0 Spot과 v1.1.0 Futures 인증서는 각자의 봉인된 candidate에만 유효하다.
- 두 인증서를 v1.2.0 통합 인증서로 합치거나 이름만 바꾸지 않는다.
- combined Full X7 gate와 공개 workflow는 완화하지 않는다.
- protected `main`의 동일 commit에서 Required CI와 release candidate build가 성공해야 한다.
- Linux x86_64/aarch64, Windows x86_64, macOS arm64 wheel과 sdist를 한 번만 빌드한다.
- Linux, Windows, macOS에서 Spot/Futures exact fixture evidence를 봉인한다.
- checksum으로 봉인한 RC asset을 재빌드 없이 stable로 승격하고 전 byte를 비교한다.
- Windows, Linux, macOS installer가 RC와 stable asset을 올바르게 선택하는지 검사한다.
- 공개 asset에는 `combined_full_x7_certified=false`인 product release contract를 포함한다.

이 릴리즈는 제품 구조, UX, CI, 검증 및 저장공간 수명주기의 완성을 공개하는
소프트웨어 릴리즈다. 새 5년 수치나 통합 인증 성능을 주장하지 않는다.

공개 결과:

- `v1.2.0-rc.1`과 `v1.2.0`은 release commit `3d1475a38629b3ab0feb13cb9b35392b8ded8874`를 가리킨다.
- stable의 12개 asset은 RC와 byte-for-byte 동일하며 공개 SHA-256 manifest 검사를 통과했다.
- Linux, Windows, macOS installer audit와 공개 Linux wheel의 full fixture가 통과했다.
- 공개 product contract는 `combined_full_x7_certified=false`를 유지한다.

## 13. M10 — Future NFI compatibility

v1.2.0 공개 뒤의 첫 제품 과제는 최신 NFI가 Native에서 막혀도 사용자가 공식
Freqtrade로 계속 실행할 수 있게 하고, 반복되는 Signal/Grind 변경을 버전별 패치가
아닌 범용 IR로 처리하는 것이다.

### 13.1 공식 fallback과 결과 상태

- Native는 모르는 의미론을 계속 `blocked_unsupported_semantics`로 차단한다.
- 사용자가 동의한 경우 pinned Freqtrade를 별도 immutable 시도 디렉터리에서 실행한다.
- Native run, 공식 결과와 `selected-result.json`은 서로 덮어쓰지 않는다.
- 공식-only 결과에는 parity 또는 Native 지원을 주장하지 않는다.
- interactive `ask`, 명시적 `official`, 완전 차단 `disabled` 정책을 제공한다.

### 13.2 범용 state-machine IR

- `order_filled`, `adjust_trade_position`, `custom_exit`의 검증된 bounded subset을
  typed IR로 컴파일한다.
- source-order guard, wallet/trade/order read, custom state read/write/delete, bounded
  loop, 추가 진입, 부분 청산과 exit를 범용 opcode로 실행한다.
- Signal 번호, Grind level 수와 tag는 전략 소스에서 추출한 데이터다.
- 알 수 없는 callback, 동적 key, 무제한 loop와 모호한 stake 방향은 fail-closed한다.
- VM 오류 또는 유효하지 않은 action은 custom state를 원자적으로 rollback한다.

### 13.3 감시와 승격

- upstream SHA가 바뀐 경우에만 Spot/Futures 검사와 AST/IR diff를 생성한다.
- SHA별 결과는 append-only compatibility ledger에 보존한다.
- 같은 blocker fingerprint는 issue와 알림을 중복 생성하지 않는다.
- Native 승격에는 서로 다른 실행 artifact, 변경 branch 도달, trade surface exact와
  full-state exact가 모두 필요하다.
- 매 upstream 변경마다 5년 인증을 실행하지 않는다. 평상시는
  `latest_checked`와 branch 중심 `quick_verified`만 갱신한다.
- 공개 성능 또는 장기 정확성 주장을 바꿀 때만 `release_certified`를 새로 만든다.

### 13.4 M10-02 무인 운영 후속

감시 workflow는 upstream SHA뿐 아니라 엔진 commit identity도 기록한다. 따라서
같은 upstream blocker를 엔진이 해결하면 다음 4시간 주기 또는 수동 force 실행에서
자동으로 다시 검사한다.

- AST/IR diff는 일반 `behavior_targets`를 생성한다.
- target과 공식 fixture coverage의 교집합으로 최소 표적 fixture를 선택한다.
- 최신 전략은 원본 fixture를 수정하지 않고 임시 sealed workload에서 실행한다.
- 변경 branch, 독립 공식/Native trade surface와 full-state가 모두 exact일 때만
  `quick_verified`로 승격한다.
- coverage가 없거나 관찰 불가능한 변경은 공식 fallback을 유지하고 정확한 gap을
  기록한다.
- 호환성 blocker와 workflow 인프라 장애는 별도 중복 방지 issue로 운영한다.
- 성공한 identity만 append-only ledger를 전진시키고 대용량 trace는 영구 branch에
  넣지 않는다.

공식 캡처 기준선은
`benchmarks/fixtures/captured/generic-state-machine-grind12-spot-2025-01-01_04`다.
이 fixture는 source에서 추출한 12단계 position adjustment를 실제 pinned
Freqtrade와 실행해 trade surface와 every-candle state projection 모두 exact parity를
요구한다. 상세 운영 계약은 `docs/future-nfi-compatibility.md`를 따른다.

이 작업은 v1.2.0으로 소급 승계되지 않는다. 구현이 완료된 commit을 포함하는 다음
제품 릴리즈에서 배포하며, 기존 Spot/Futures 5년 인증 경계도 자동 승계하지 않는다.

## 14. M11 — Futures branch discovery와 v1.3.0

M10의 4시간 빠른 감시는 기존 fixture가 닿는 변경을 즉시 검증한다. Futures에서
coverage gap이 남을 때는 장시간 작업을 fast lane에 넣지 않고 별도의 bounded
deep-search로 넘긴다.

### 14.1 탐색 계약

- 범위는 `planning/futures-discovery-policy.json`에서만 읽는다.
- 이전 5개 완료 연도를 3개월 shard로 나누어 최신순 검색한다.
- listing-aware universe 최대 80 pairs, worker 1개, 실행당 7,200초를 넘지 않는다.
- request identity는 upstream/engine/source/policy/target/time window를 묶는다.
- budget 소진 시 다음 shard cursor를 남기고 같은 identity에서만 재개한다.
- 새 identity를 우선하며 superseded cursor와 증거는 덮어쓰지 않는다.
- 제거된 target과 새 결과만으로 관찰할 수 없는 callback은 추측 검색하지 않는다.
- 검색 hit는 승격 증거가 아니며, 최소화한 독립 공식/Native capture가 변경 branch,
  trade surface와 full-state에서 모두 exact여야 한다.

### 14.2 무인 운영과 저장공간

- 심층 workflow는 nightly와 수동 실행을 제공하고 동시 실행은 하나로 제한한다.
- terminal semantic gap과 인프라 장애는 서로 다른 fingerprint issue로 관리한다.
- 정확한 candidate는 30 MiB 이하의 allowlist된 fixture/evidence만 Draft PR로
  만들고 required CI를 요청한다.
- GitHub Actions는 PR 생성 권한만 사용하며 자동 승인 또는 merge하지 않는다.
- request/report/cursor는 append-only ledger에 보존하고 raw candles/cache/trace는
  영구 branch나 PR에 올리지 않는다.
- candidate artifact 보존 기간은 30일이다.
- budget/인프라 실패 로컬 run은 clean lifecycle에서 회수 가능하며, 완료 보고서와
  공식 Oracle/evidence는 기본 보호한다.

### 14.3 v1.3.0 릴리즈 경계

M11 완료본은 v1.3.0 `product` 릴리즈로 공개한다. v1.2.0과 동일하게 protected
`main`의 동일 commit, Required CI, 3OS wheel/fixture evidence, checksum으로 봉인한
RC와 stable의 byte identity, installer audit를 요구한다.

v1.3.0은 최신 NFI 감시·공식 fallback·범용 state-machine IR·Futures 자동 fixture
발견을 배포한다. 새 5년 Spot/Futures 통합 인증을 만들지 않으며 공개 contract의
`combined_full_x7_certified=false`를 유지한다. 기존 v1.0.0 Spot과 v1.1.0 Futures
인증서는 각자의 봉인된 candidate에만 유효하다.

## 17. 작업 단위 규칙

각 작업은 다음 형태로 관리한다.

```text
목표
→ 변경하지 않을 계약
→ 입력 evidence
→ 구현
→ 관련 테스트
→ golden SHA 검증
→ 성능 영향
→ 문서
→ 커밋
```

커밋 전에 반드시 확인한다.

- 사용자 소유 untracked 파일을 포함하지 않았는가
- `.nfi` runtime/evidence가 stage되지 않았는가
- 공식 ZIP이나 인증서를 수정하지 않았는가
- 하드코딩된 strategy/pair/date 결과 분기가 없는가
- 모듈 이동과 최적화가 섞이지 않았는가
- 실패 시 기존 성공 evidence를 보존하는가

## 18. 최종 완료 정의

이 로드맵은 다음 상태에서 완료된다.

- v1.1 계약을 자동 검증하는 regression manifest가 있다.
- 검증 상태와 인증 fingerprint가 제품 기능으로 통일돼 있다.
- `.nfi`를 안전하게 조사하고 정리할 수 있다.
- Python과 Rust 대형 모듈이 책임별로 분리돼 있다.
- 새 구조에서 측정된 최적화가 exact parity를 유지한다.
- 결과 artifact와 한 줄 UX가 일반 사용자에게 충분하다.

- 지원 가능한 stateful callback은 버전/Signal 하드코딩 없이 범용 IR로 실행된다.
- Native 지원 승격은 독립 실행의 trade와 full-state exact 증거를 요구한다.
- PR, nightly, 장시간 인증, release workflow의 신뢰 경계가 분리돼 있다.
- v1.2.0 product candidate의 3개 OS 배포 증거와 release asset identity가 봉인돼 있다.
- v1.2.0 RC와 stable asset이 byte-for-byte 동일하고 설치 검증을 통과한다.
- Futures coverage gap이 bounded/resumable discovery로 이어지고 exact candidate만
  Draft PR로 제출된다.
- v1.3.0 product release가 이 운영장치를 배포하되 통합 Full X7 인증을 주장하지
  않는다.
- 최신 동일 candidate Spot+Futures 인증을 다시 승인하기 전까지 통합 Full X7
  release는 공개하지 않고 기존 mode별 인증 경계를 유지한다.
